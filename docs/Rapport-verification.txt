VALIDATION WINDOWS EXIGEE AVANT LA LIVRAISON
Le script build-tools/Invoke-WindowsCi.ps1 sépare quatre étapes obligatoires.
Chaque processus a un délai maximal, un code de sortie contrôlé et, pour
les suites de tests, un résumé de réussite attendu. Un échec bloque la suite.

1. BclChecks relance onze suites (453 contrôles attendus) sur données synthétiques :
   démarrage, configuration, dashboard, dispositions, aperçu, techniciens,
   villes, tournées, requêtes, import et export. Le code de production est utilisé.
2. WpfChecks publie puis exécute WindowsStartupChecks sur un bureau Windows.
   Il construit les vues réelles et vérifie leur rendu dans les deux thèmes.
   Les scénarios demandent 1440 × 900 à 100 % en clair, 960 × 720 à 150 %
   en clair et 1280 × 850 à 125 % en sombre. Windows peut borner la fenêtre
   à son bureau disponible ; les dimensions effectives sont journalisées.
   Ils contrôlent le défilement du dashboard personnel, les cartes sans
   ascenseur interne actif, l’expansion météo et l’absence de recouvrement.
   Une liste de 43 catégories doit rester accessible sur toutes ses pages,
   avec recherche hors première page, indices corrects et retour au dashboard.
3. BuildPack fabrique les ZIP PROD et DEV ; contrôle leur contenu, toutes les
   empreintes SHA-256, le commit source et l’identité de leur exécutable.
4. PackStartup extrait PROD dans un espace temporaire isolé et lance son EXE.
   Le premier lancement exige le marqueur [PRÊT], une fenêtre principale
   visible, une fermeture normale, le code 0 et les réglages synthétiques
   strictement inchangés. Un état GLPI Pilot déjà présent entraîne un refus.
   Deux redémarrages supplémentaires exercent les vrais boutons par Windows
   UI Automation : −, +, retour à 100 %, limites 75/150 %, commandes dans
   une fenêtre 960 × 720 à 150 %. Le zoom laissé à 110 % doit être retrouvé
   au redémarrage suivant puis remis à 100 % par le bouton réel.
   Source, thème, dossier d’export et identité synthétiques restent préservés.

PORTEE ET LIMITES
Les contrôles utilisent exclusivement des données et préférences synthétiques.
Ils n’ouvrent pas le navigateur métier, n’authentifient aucun compte SSO et
ne se connectent pas au portail réel de l’utilisateur. Les captures ne
contiennent donc pas ses tickets. Le SSO, les droits, la version du portail
et le maintien au premier plan sur le poste restent à confirmer sur ce poste.
Une absence de bureau Windows interactif est signalée comme non-exécution,
jamais comme réussite. Les résultats définitifs sont ceux du run du commit
livré, avec ses journaux, ses captures et les empreintes des deux ZIP.
