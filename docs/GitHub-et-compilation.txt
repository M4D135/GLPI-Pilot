GLPI Pilot 2.1.0 — packs PROD et DEV, compilation Windows

DEUX PACKS COMPLETS
Chaque ZIP contient exactement GLPI-Pilot.exe et le dossier wad à sa racine.
PROD : exécutable autonome, pilote Windows complet, guide, diagnostics,
licences et empreintes SHA-256. Aucune installation de .NET n’est nécessaire.
DEV : le même exécutable et le même pilote, avec les sources, tests et outils
de compilation dépliés sous wad/sources. Tout reste rangé dans wad.
Aucun profil SSO, réglage personnel ou relevé métier n’est inclus.
Edge ou Chrome doit être installé et autorisé sur le poste utilisateur.

TELECHARGER
Dépôt : https://github.com/M4D135/GLPI-Pilot
Packs : https://github.com/M4D135/GLPI-Pilot/releases
Choisir le ZIP PROD pour utiliser le logiciel, DEV pour son développement.
La commande GitHub Code > Download ZIP télécharge uniquement les sources.
Extraire le pack entier et conserver wad à côté de GLPI-Pilot.exe.

COMPILER SOUS WINDOWS
Prérequis de développement : SDK .NET 10 stable, PowerShell 7.2 ou plus,
accès aux dépendances NuGet. Depuis wad/sources du pack DEV, ou la racine
des sources du dépôt, lancer dans PowerShell :
  ./build.ps1
Cette commande produit les deux ZIP PROD et DEV dans artifacts.
Le script refuse de remplacer un pack déjà présent. Choisir un autre dossier :
  ./build.ps1 -OutputDirectory ./artifacts/release-suivante
Le pack DEV peut ainsi reconstruire les deux distributions.

WORKFLOW GITHUB ACTIONS
.github/workflows/windows.yml exécute sous Windows x64 :
1. Dix-huit suites métier, configuration, historique, assistance et mise à jour.
2. Collecte, SSO simulé, reprise, formulaires et DOM sur pages synthétiques.
3. Vrais contrôles WPF sur bureau interactif, plusieurs tailles/thèmes/zooms.
4. Construction et contrôle des packs PROD/DEV, empreintes et commit source.
5. Démarrage du pack PROD, instance unique, boutons et persistance du zoom.
6. Remplacement réel d’une copie du pack, verrouillage et retour arrière après
   échec de démarrage provoqué, dans un dossier temporaire de test.
7. Promotion des mêmes ZIP en Release après réussite de tous les contrôles.
Le job de test utilise contents:read. Le job de publication dispose de
contents:write uniquement pour promouvoir les artefacts contrôlés de main.
Une version déjà publiée pour un autre commit n’est pas remplacée.

Les journaux sont joints également en cas d’échec ; ils sont conservés
14 jours. Les artefacts de packs sont conservés 30 jours. Les captures PNG WPF ne contiennent que des données synthétiques.
Les contrôles du pack refusent tout état GLPI Pilot préexistant sur le runner.
Aucun portail GLPI réel, aucune session SSO d’entreprise ni aucun fournisseur
routier, météo ou d’assistance n’est contacté pendant ces tests.

SIGNATURE FACULTATIVE
build-tools/Sign-Release.ps1 est exécuté après publication de l’EXE et avant
calcul des empreintes. GLPI_SIGN_CERT_THUMBPRINT désigne un certificat de
signature avec clé privée dans CurrentUser/My ; GLPI_SIGN_TIMESTAMP_URL
est obligatoire lorsqu’une signature est demandée. Signature, certificat
et horodatage sont contrôlés. Sans certificat configuré, le pack est non signé.
La mise à jour peut exiger une signature et une empreinte d’éditeur approuvée.

PORTEE DES VERIFICATIONS
La compilation croisée Linux pour Windows ne prouve pas un démarrage WPF.
La présence d’un workflow ou d’un commit ne prouve pas sa réussite.
Consulter Rapport-verification.txt, les journaux du run et wad/version.json
pour identifier le code et les résultats exacts des ZIP publiés.
SSO privé, extensions GLPI, veille et moniteurs du poste restent à valider
sur l’installation réelle ; ils ne sont pas remplacés par des fixtures.

EN CAS DE NON-DEMARRAGE
Dans le pack extrait, lancer wad/support/DIAGNOSTIC_DEMARRAGE.cmd.
Ce lanceur observe le démarrage et ouvre son rapport dans le Bloc-notes.
Il conserve les réglages et le profil du navigateur. Le diagnostic permet
d’identifier l’étape exacte en échec sur le poste concerné.
